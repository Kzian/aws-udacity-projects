Design decision. The choice I thought hardest about was how the MemoryHook stores conversations. Before each turn, the hook prepends retrieved memories to the customer’s message as a “Customer Context” block. If I had saved the message as it appeared in the agent’s history, that injected block would have been written back into memory as though the customer had said it, so each turn would feed memories back into themselves and make recall noisier. Instead the hook saves the customer’s original words together with the assistant’s reply. Test 4 shows it working: a brand-new session (s-B) recalled the name “Jane” and the preference for concise answers from session s-A. I also wrapped the memory calls in error handling so a memory outage degrades an answer instead of breaking the request.

Challenge. When I added the refund-processor Lambda target to the Gateway, creation failed with a ValidationException saying the Gateway’s execution role could not invoke the function. Before changing any policy, I retried the creation, and it succeeded, which points to IAM propagation delay for the role the console had just created. Earlier, target names with underscores were rejected because the console allows only letters, digits and hyphens, so the tools appear as order-tracker___get_order. Both taught me to check naming rules and allow for IAM’s eventual consistency before changing permissions.

Production consideration. The Gateway uses the NONE authorizer, which is acceptable only in this lab. The tools can issue refunds, so in production I would require JWT or IAM authentication, cap refund amounts, and require human approval above a threshold. I would add CloudWatch alarms on tool errors and budget alerts on Bedrock invocations and the Knowledge Base’s vector storage, which keeps costing money while idle.
